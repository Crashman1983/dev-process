# v2.85 — Ein Host, der einen Stack nicht kann

issue: #373
tier: 3

## Anlass

Downstream (Kenni #2844) kann ein Mac-Agent den Backend-Stack nicht ausführen: Der Preflight des Projekts fällt dort durch (`pidfd` fehlt, `df` unlesbar), und die Suite ist auf diesem Host nicht bestehbar. Jeder Branch-Push, der den Stack wählt, wird mit Exit 2 abgewiesen. Der einzige Weg vorbei ist `PROCESS_SKIP=tests` mit dem Wort des Owners. Das ist an einem Tag dreimal passiert (#2840, #2843, #2845). Die Merge-Suite fährt ohnehin der Zug auf dem Gate-Host; der Skip schützt nichts und kostet nur Rückfragen.

Owner-Entscheidung: „stimme den Vorschlägen zu“. Das Template liefert die Host-Bedingung je Stack, den Vermerk „fällig auf dem Gate-Host“ und einen Pflichtgrund für `PROCESS_SKIP`. Kenni repariert seinen Preflight und konfiguriert die Stacks.

## Umfang

| Paket | Inhalt |
|---|---|
| H | Host-Bedingung je Stack: Ein Stack, den der Host nicht kann, wird beim Branch-Push vermerkt statt abgewiesen. Merge-Push und Zug bleiben unverändert. |
| S | `PROCESS_SKIP` braucht einen Grund im Protokoll. |

Nicht in diesem Release:
- ein Weg, auf dem ein Merge-Push etwas aufschiebt;
- ein Vermerk, der zwischen Hosts reist (siehe H4);
- Änderungen am Zug.

## H — Host-Bedingung je Stack

### Aufgaben

- [ ] H1: **`testing_config`.** Ein Stack darf `preflight` (argv) tragen, mit demselben Timeout wie der globale Preflight (`preflight_timeout`). Exit `3` heißt „dieser Host kann den Stack nicht“ (`HOST_UNSUITED`), jeder andere Code ungleich 0 heißt „der Host ist kaputt“. Der globale Preflight bleibt, wie er ist: Er läuft zuerst, und rot weist ab.
- [ ] H2: **`test_select.run`, Branch-Klasse.** Nach dem globalen Preflight läuft der Preflight jedes Stacks, der Arbeit hat, einmal.
  - 0: Der Stack läuft.
  - 3: Seine Arbeit entfällt. Er wird als **fällig auf dem Gate-Host** genannt (`test_select: owed on the gate host — backend (its preflight: this host cannot run it)`), und die übrigen Stacks laufen.
  - anderes: Exit 2 wie heute („fix the host“).
  - Bleibt keine Arbeit übrig, ist das Ergebnis grün mit Vermerk, nicht „nothing to test“.
- [ ] H3: **`test_select.run`, Merge-Klasse.** Vor `merge_suite` oder den `full`-Befehlen läuft der Preflight **jedes** Stacks. Eine 3 weist ab (Exit 2): „a merge runs every stack; this host cannot run backend“. Nichts wird aufgeschoben.
- [ ] H4: **Vermerk, maschinenlesbar.** Wurde ein Stack aufgeschoben, schreibt `test_select` eine Zeile in `<git-common-dir>/process-owed.jsonl`: `{"ts", "head", "branch", "stacks": [...], "host"}`. Das ist derselbe Ort wie Stempel und Gate-Events: lokal, nicht im Repository.
  - **Kein Push-Zertifikat** für diesen Baum, wenn ein Stack aufgeschoben wurde.
  - **Stempel** in `pre_push` tragen die aufgeschobenen Stacks im Schlüssel. Ein Push desselben Stands auf einem Host, der alle Stacks kann, ist also kein Stempeltreffer.
  - Der Vermerk reist nicht zwischen Hosts. Das reicht, weil die Merge-Suite im Zug ohnehin alle Stacks fährt; der Vermerk ist Sichtbarkeit, keine Bedingung.
- [ ] H5: **Sichtbarkeit.** `make_review_bundle` nennt die aufgeschobenen Stacks der Commits im Range, soweit dieser Klon sie kennt („owed on the gate host: backend at abc123 (mac)“). Kennt er keine, sagt es nichts. `human_digest` nennt sie im Abschnitt „Waiting for you“ nicht, weil der Zug sie ohnehin fährt.
- [ ] H6: **Doku.** `testing.md` beschreibt den Preflight je Stack, den Code 3 und die Grenze „Merge schiebt nie auf“. `train.md` braucht nichts.

### Tests (rot vor dem Fix)

1. Branch-Push wählt zwei Stacks; der Preflight von `backend` gibt 3: `frontend` läuft, `backend` nicht, Exit 0, Vermerk in der Ausgabe und in `process-owed.jsonl`, kein Push-Zertifikat.
2. Derselbe Preflight gibt 1: Exit 2, kein Test lief.
3. Merge-Push: Der Preflight eines Stacks gibt 3, Exit 2, keine Suite lief.
4. Nur der aufgeschobene Stack hatte Arbeit: Exit 0 mit Vermerk, nicht „nothing to test“.
5. Ein Stempel mit aufgeschobenem Stack ist für denselben Stand ohne Aufschub kein Treffer.
6. Ohne Stack-Preflight ändert sich nichts (bestehende Tests bleiben grün).
7. Das Bundle nennt den Vermerk aus `process-owed.jsonl` für einen Commit im Range.
8. `testing_config`: ein Stack-`preflight`, das kein argv ist → `ConfigError`.

## S — `PROCESS_SKIP` braucht einen Grund

### Aufgaben

- [ ] S1: `PROCESS_SKIP=…` verlangt `PROCESS_SKIP_REASON="<Grund>"`, wie `PROCESS_OWNER_OVERRIDE` einen Grund verlangt. Ohne Grund wird der Push abgewiesen: „a skip needs its reason“. Das gilt für `pre_push._owner_only` und für den Skip der Gates auf main in `merge_route`.
- [ ] S2: Die Protokollzeile trägt den Grund: `PROCESS_SKIP=tests: <Grund>`.
- [ ] S3: Doku in `testing.md` („Skipping“) und `train.md` („Skipped gates“).

### Tests

9. `PROCESS_SKIP=tests` ohne Grund → abgewiesen, kein Eintrag im Protokoll.
10. Mit Grund → angenommen, die Zeile trägt den Grund.
11. Der Skip der Gates auf main ohne Grund → abgewiesen.

## Regressions-Linse

- **„A missing check reported as passed“:** Ein aufgeschobener Stack heißt nie grün ohne Vermerk. Die Ausgabe nennt ihn, ein Zertifikat entsteht nicht, der Stempel trägt ihn.
- **Merge-Weg:** Merge-Push und Zug fahren jeden Stack. Ein Host, der einen Stack nicht kann, kann nicht mergen.
- **Preflight-Semantik:** Der globale Preflight bleibt unverändert. Neu ist nur ein Code mit Bedeutung beim Preflight je Stack.
- **Owner-Skip:** Er wird strenger (Pflichtgrund), nie lockerer.

## Update

Reines Update. Ohne Stack-`preflight` ändert sich nichts außer dem Pflichtgrund für `PROCESS_SKIP`. Kenni trägt den Host-Check für `backend` als Stack-Preflight ein (Exit 3 auf dem Mac) und kann den globalen Preflight dann auf das beschränken, was jeder Host können muss.
