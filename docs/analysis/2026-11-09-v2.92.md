### K — Konfiguration und Layout (Owner-Entscheidung „1“)

- [ ] K1 `[design]` **Eine Konfigurationsdatei.**
  - Die Template-Datei `docs/process/feature-registry.json` hat einen Kommentar je Schlüssel. Die Projektwahl liegt in `docs/process/feature-registry.local.json` und wird Abbildung für Abbildung darübergelegt, wie bei `model-policy.local.json`.
  - Ohne Projektdatei gilt das heutige Template-Verhalten. Einzige Ausnahme sind die Item-IDs (I1).
  - Schlüssel mit Standardwerten:
    - `layout`: `"flat"` (heute) | `"capabilities"` (Kenni);
    - `root`: `"docs/process/feature-registry"`;
    - `id_pattern`: `"^STORY-\\d{4}$"`, im Layout `capabilities` mit `{prefix}`, z. B. `"^{prefix}-US-\\d{3}$"`;
    - `prefixes`: Verzeichnis → Präfix, ohne Rückfall. Ein fehlendes Verzeichnis ist ein Fehler, Kenni trägt `captures`, `clients` und `engagements` nach;
    - `story_fields`: Pflicht-Textfelder, Standard `["title", "story"]`, Kenni `["title", "as_a", "i_want", "so_that"]`;
    - `story_tests`: `"tests"` (Liste, heute) | `"test_mapping"` (Zuordnung Plattform/Schicht → Liste);
    - `surfaces`: erlaubte Plattformen, Standard keine;
    - `shared_proof_layers`: Standard `[]`, Kenni `["backend"]`;
    - `issues`: `{"field": "issue" | "issues", "pattern": null | "^#\\d+$"}`;
    - `story_status`: `null` (heute: `status` bleibt ein abgeschafftes Feld) | `{"values": […], "deferred": "deferred", "covered_requires_issue": true}`;
    - `derived_status_areas`: Bereiche mit scharfer Ableitung. Im Layout `flat` gilt `true`/`false` für das ganze Inventar;
    - `test_ref_roots`: erlaubte Präfixe für Test-Verweise, Standard keine Einschränkung;
    - `planned_refs`: `false` | `true` (`planned:#n:<text>`);
    - `node_check`: `"note"` (Standard) | `"hard"` (Kenni);
    - `retired_fields`: Standard `["status", "blocked_by", "parent"]`. Mit `story_status` fällt `status` heraus. Kenni ergänzt `backlog`;
    - `strict_item_tests`: `false`.

### I — Items nach #404 A, F, G

- [ ] I1 `[mechanical]` **Item-ID (AC-1, AC-14).**
  - `id` ist Pflicht, folgt `^AC[1-9]\d*$` und ist eindeutig je Story.
  - Das gilt auch ohne Projektdatei. Der Template-Seed trägt die ID schon. Für Altbestände gibt es `--assign-ids` (M1).
  - Verweise haben die Form `<Story-ID>#<Item-ID>`.
- [ ] I2 `[mechanical]` **Item-Felder (AC-2, AC-3, AC-15, AC-22).**
  - **`text`** ist Pflicht.
  - **`surfaces`** ⊆ den Plattformen der Story, ohne Story-Plattformen ⊆ `surfaces` der Konfiguration.
  - **`state`** ist `proven`/`target` oder eine Zuordnung je Plattform. Ist eine Plattform `target`, ist `issue` Pflicht, im Format von `issues.pattern`.
  - **`tests`** ist eine Zuordnung je Plattform oder je `owned_by`-Schicht. Eine einfache Liste ist nur erlaubt, wenn das Item genau eine Plattform hat.
  - **`owned_by`** nimmt einen Wert aus `shared_proof_layers` an. Ein Schicht-Schlüssel ohne passendes `owned_by` ist ein Fehler.
  - **`design`** wird angenommen und erst mit #404 B geprüft (AC-4 folgt dort).
  - Mit `strict_item_tests` wird ein Item ohne `tests` zum Fehler, sonst bleibt es ein Hinweis, gesammelt in einer Zeile je Bereich.
- [ ] I3 `[design]` **Abgeleiteter Status (AC-16, AC-21, AC-22, AC-23).**
  - Gilt nur bei gesetztem `story_status`.
  - **Abgeleitet** wird so:
    - `covered`, wenn jede Item-Plattform belegt ist;
    - `partial`, wenn belegte und Ziel-Plattformen gemischt sind;
    - `planned`, wenn keine belegt ist.
  - **Belegt** heißt `proven` *und* ein existierender Test unter dem eigenen Schlüssel oder unter der `owned_by`-Schicht.
  - `deferred` ist ausgenommen.
  - In einem Bereich aus `derived_status_areas` ist eine Abweichung ein Fehler, sonst ein Hinweis.
  - Der Report nennt je Bereich den Anteil der Items mit `owned_by`.
  - `--preview-derived <bereich>` zeigt vor dem Scharfschalten, was dann scheitern würde. Dazu gehören die Item-Plattformen ohne jeden erfüllbaren Test-Schlüssel (AC-23).
  - **Zurückgestellt:** AC-17 (Ziel mit geschlossenem Issue als Hinweis). Ein Gate läuft offline; eine Netzabfrage wäre eine neue Abhängigkeit. Der natürliche Ort ist der Tower, ein eigener Schritt nach v2.92.
- [ ] I4 `[design]` **Stabile IDs (AC-18, AC-19, AC-20).**
  - Auf Story-Ebene steht `retired: [{"id": "AC9", "split_into": ["AC31", "AC32"]}]`.
  - Verglichen wird gegen die merge-base mit der Integrationsbasis (`check_review.integration_ref`, ein Besitzer).
  - Verschwindet eine ID, muss sie in `retired` stehen. Eine neue ID steht nicht in `retired` und ist größer als alle bisherigen.
  - `split_into` nennt existierende IDs derselben Story. Registry-Verweise lösen über `retired` auf.
  - **Flacher Klon:** `git fetch --deepen` in Schritten bis zur merge-base, höchstens 3 Versuche. Gelingt das nicht, gibt es einen Hinweis mit der fehlenden Basis, nie ein stilles OK.

## Regressions-Linse

- **I1 ist die einzige Verschärfung ohne Projektwahl:** Items ohne `id` werden rot. Der Template-Seed hatte die ID seit jeher. Altbestände bringt `--assign-ids` in einem Schritt in Ordnung; das Update nennt den Befehl.
- **K4 `::node`** ist standardmäßig ein Hinweis. Ein Projekt mit veralteten Knoten wird nicht rot, bevor es `hard` wählt.
- **Owner-Entscheidung, bewusste Änderung des Grundsatzes:** Die Registry nimmt Ziel-Items auf. `status` bleibt ohne `story_status` abgeschafft; mit `story_status` wird er geprüft und, je Bereich, abgeleitet.
- **Kenni ist bis zur Umstellung unberührt**, weil sein eigener Checker läuft.
- **T2** kann Token-Summen gegenüber v2.91 senken: Nachrichten vor `started` zählten bisher mit. Das ist eine Korrektur.
