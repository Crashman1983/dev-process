## Aufgaben v2.98

- [ ] A1 `[design]` **Ein `(#N)` im Betreff beansprucht N nur für den eigenen Branch (#424 Fall 2).**
  - Der Anspruch eines Commits gilt, wenn N das Issue seines Branches ist (`branch_issue`) oder ein Plan des Branches N deklariert (`own_plans`); sonst ist `(#N)` ein Verweis und wird als Notiz genannt („commit … names #N, not this branch's issue — read as a reference“).
  - **Welcher Branch:** im Zug der Passagier, dessen Merge den Commit bringt (zweiter Elternteil eines `train: merge <branch>`-Commits im Batch); sonst der Branch von HEAD (`rev-parse --abbrev-ref`), wie `finish` ihn kennt. Ist kein Branch bestimmbar (losgelöster HEAD ohne Zug-Merge), gilt die heutige Regel.
  - Schließende Wörter (`Closes #N`) bleiben ein Anspruch: wer ein Issue schließt, beansprucht es.
  - Dieselbe Regel in `finish.py` (:266, :274-277).
- [ ] A2 `[design]` **Im Zug wird ein Passagier nach seinem eigenen Plan beurteilt (#424 Fall 1).**
  - Erst der Befund: aus dem Zug-Log von 20261116-0544 (vom Steward an #424) die Zeilen des Review-Gates; daraus der Test, der rot ist.
  - Dann der Fix an der Stelle, die der Befund nennt. Erwartet (zu bestätigen): Bei zwei Passagieren, die dieselbe Datei in getrennten Hunks ändern, erzeugt der Merge einen Stand, den keine Review sah, und `_history` liest ihn als Code des Trägers oder des Mitfahrers. Gilt das, wird ein sauber gemergter Hunk-Mix zweier reviewter Passagiere als reviewt anerkannt, wenn jeder Hunk auf den reviewten Stand seines Passagiers zurückgeht (wie `test_two_passengers_on_hunks_of_one_file_are_both_reviewed`, test_stale_review.py:490, für mehr als einen Hunk-Typ).
  - Bestätigt der Befund das nicht, wird A2 neu geschnitten und dem Owner vorgelegt, bevor Code entsteht.
- [ ] B1 `[design]` **Eine volle Platte ist im Zug kein roter Passagier (#425).**
  - `disk_refusal` zieht nach `process_git.py` (Kern; dispatch nutzt es von dort), damit Zug und dispatch dieselbe Regel lesen.
  - Vor jedem Suite-Lauf prüft der Zug die Platte unter seinen Worktrees. Über der Grenze: die Runde endet `result="environment"`, `red_path="disk-full"`, niemand beschuldigt, nichts gemergt, Grund genannt.
  - Endet ein Suite-Lauf rot und ist die Platte danach über der Grenze, zählt er als abgebrochen (Regel aus v2.95: warten, einmal neu, dann frische Basis) — mit der Abbruch-Zeile `disk-full <use>%`.
  - `dispatch.py` schreibt bei einer Plattenverweigerung eine Zeile nach `$PROCESS_SUITE_ABORT`, falls gesetzt; so wird eine verweigerte verschachtelte Sitzung in der Suite ein Abbruch.
  - `train-phases` zählt `disk-full` getrennt von Preflight, Abbruch und Passagieren.
- [ ] D1 `[design]` **`plan` liest nur Branches, die einsteigen können (#426).**
  - **Zuerst messen:** `tools/bench_train_plan.py` bekommt `--stale-ahead N` (ungemergte Branches mit eigenen Commits ohne Bericht, wie in Kenni). Gemessen wird `plan --json` vorher mit 0, 50 und 200 solchen Branches; der Anteil je Schritt (Vorab-Schleifen, Paarschleife, Hauptschleife) über einen Zähler je Abschnitt, nur im Bench-Lauf.
  - **Dann eingrenzen:** Ein Branch geht nur in die teuren Schleifen, wenn er einsteigen kann — sein letzter Bericht ist `review-pass` (die heutige Bedingung für eligible) oder er ist ein Kandidat des laufenden Zugs. Die übrigen werden vor den Schleifen nur gezählt (`not ready: N`), wie heute die gemergten (`no_lead`).
  - `own_plans` läuft je Branch einmal; das Ergebnis geht an `_deviations` weiter.
  - Kein Zwischenspeicher zwischen Läufen in diesem Release; erst wenn die Messung nach der Eingrenzung noch Zeit in Branches zeigt, die einsteigen können.
  - Die Entscheidungen bleiben gleich: dieselben Kandidaten, dieselben Konflikte (bestehende Tests, dazu ein Test mit stale Branches).
- [ ] E1 `[mechanical]` **Doku.** `commits.md`: `(#N)` beansprucht nur das Issue des eigenen Branches; `train.md`: `disk-full`; `testing.md` („Unmeasurable is not red“): volle Platte; `telemetry.md` (`train-phases`). CHANGELOG/NEWS mit Marken.
