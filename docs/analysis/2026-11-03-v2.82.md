# v2.82 — Spec-Kit-Skills erreichen jeden Klon

issue: #363
issue: #365
tier: 3

## Anlass

Das Modul `speckit` richtet Spec Kit über `specify init` ein. Der Befehl schreibt die `/speckit-*`-Skills in das Skill-Verzeichnis des Harness, bei Claude Code nach `.claude/skills/`. Laut Moduldoku braucht zur Laufzeit nichts das CLI. Das stimmt nur, wenn die Skills committet sind.

In Kenni ist das nicht der Fall:

- `.gitignore:26` schließt `.claude/skills/` aus, seit `3bcd9b9bcc` (2026-04-15, „per-user Claude Code state“). Das war vier Monate vor Spec Kit.
- `specify init` lief am 2026-08-08. Die Skills landeten im ignorierten Verzeichnis. `git status` zeigte nichts, es gab weder Fehler noch Hinweis.
- `.specify/integrations/claude.manifest.json` listet zehn Skill-Dateien, keine davon ist getrackt.
- Skripte und Vorlagen unter `.specify/` sind dagegen committet.

Jeder frische Klon hat deshalb kein `/speckit-specify`, `-clarify`, `-plan` und `-tasks`. Das gilt für Cloud-Sessions, Worktrees und einen zweiten Host. Zurück kommen die Skills nur, wenn man `specify-cli` installiert. Das kann eine Sandbox verweigern; der Owner ist in einem Projekt genau daran gescheitert.

Ein Test in einem Scratch-Repo zeigt außerdem: Die Ausnahme aus #363 (`!.claude/skills/speckit-*/` neben `.claude/skills/`) wirkt nicht. Git schließt nichts wieder ein, dessen Elternverzeichnis ausgeschlossen ist. Erst `.claude/skills/*` mit der Ausnahme danach macht die Skills sichtbar (Kommentar auf #363).

## Begriffe

- **Integrations-Manifest:** `.specify/integrations/<integration>.manifest.json`. Spec Kit 0.16 schreibt es je Integration. Unter `files` stehen die installierten Pfade (POSIX-Schreibweise) mit Hash. `speckit.manifest.json` ist der Kern (Skripte und Vorlagen), kein Harness.
- **Aktive Integrationen:** `installed_integrations` aus `.specify/integration.json`. Ist die Datei nicht lesbar, gelten alle Harness-Manifeste, und ein Hinweis sagt das. Manifeste einer früher installierten, inzwischen ersetzten Integration werden nicht gelesen.
- **Spec-Kit-Skill-Datei:** ein Pfad aus einem aktiven Harness-Manifest, dessen Pfadteil mit `speckit-<name>` oder `speckit.<name>` beginnt, also `.claude/skills/speckit-plan/SKILL.md` oder `.agents/commands/speckit.plan.md`. Der Name ist das erste Wort nach `speckit` und dem Trenner. Das **Skill-Verzeichnis** ist der Pfad bis vor diesen Teil (`.claude/skills`, `.agents/commands`).
- **Bewusst entfernt:** `constitution`, `implement` und `taskstoissues`. Das Setup löscht sie (`speckit.md`, „Setup“). Sie stehen weiter im Manifest.
- **Verwaist:** eine getrackte Datei in einem Skill-Verzeichnis, deren Pfad mit `speckit` beginnt und die in keinem aktiven Manifest steht, etwa ein Skill, den eine neuere Spec-Kit-Version umbenannt hat.

## Paket P — Gates ohne Paket-Index (#365)

**Anlass.** Das Sandbox-Experiment (unten) zeigte es so:

- Ein Kind-Gate mit PEP-723-Block geht über `gate_invoke.child_argv` immer über `uv run --script`, sobald `uv` auf PATH liegt. Das passiert auch dann, wenn der laufende Interpreter die Abhängigkeit schon hat (System-PyYAML).
- Ohne Zugang zu PyPI bricht uv mit rc 2 ab. Der Gate-Abschnitt bleibt leer, uvs Fehler steht unzugeordnet auf stderr, und die Zusammenfassung sagt nur `FAILED gates: …`.
- Der Pre-push-Hook fährt dieselben Gates, also wird jeder Push verweigert.
- Der Runner selbst prüft schon heute erst den Interpreter (`gate_runner_argv`, `find_spec("yaml")`). Nur die Kinder prüfen ihn nicht.

Realistisches Modell (Owner): GitHub und die Modell-API sind erreichbar, PyPI nicht. Die CI auf GitHub ist nicht betroffen.

**Aufgaben.**

- [x] P1: `gate_invoke.declared_dependencies` liest den PEP-723-Block mit `tomllib` (stdlib ab 3.11).
  - Ohne `tomllib` fällt es auf die Zeichenketten in Anführungszeichen zurück, nie auf das Komma: `["pyyaml>=6,<7"]` ist eine Anforderung, nicht zwei.
  - Neu: `declared_python(path)` liefert `requires-python`.
- [x] P2: `gate_invoke.child_argv` startet ein Kind direkt mit `cmd[0]`, wenn alle folgenden Bedingungen gelten. Sonst bleibt `uv run --script`.
  - `cmd[0] == sys.executable`, als Zeichenkette verglichen und nicht aufgelöst: Ein venv-Python ist ein Symlink auf das Basis-Python, hat aber andere Pakete.
  - Der laufende Interpreter erfüllt `requires-python`.
  - Jede deklarierte Anforderung ist belegt. Belegt heißt:
    - Die Distribution ist installiert (`importlib.metadata`).
    - Ihre Version besteht nur aus Ziffern und Punkten.
    - Jeder Vergleich nutzt `>=`, `>`, `<=`, `<`, `==` oder `!=` mit Null-Auffüllung (`6.0` == `6.0.0`).
    - Mindestens eines ihrer Top-Level-Module ist auffindbar (`packages_distributions` + `find_spec`).
  - Nicht belegbar und damit über uv laufen: Extras, Marker, `~=`, `===`, Wildcards, Vor- und Nachversionen (`rc`, `.post`, `.dev`), Epochen und eine Distribution ohne auffindbares Modul.
- [x] P3: Startproblem benennen. Ein Lauf über `uv run --script` (im `gate_runner`) oder über `uv run` (Runner-Start im Pre-push-Rahmen `pre_push._gates`) gilt als Startproblem, wenn alle drei Bedingungen zutreffen:
  - Er endet mit rc ≠ 0.
  - stdout ist leer.
  - stderr trägt uvs Fehlerform: eine Zeile beginnt mit `error:`, `  Caused by:` oder `×`.

  Dann sagt der Abschnitt: Start über uv für die deklarierten Abhängigkeiten, uv vor dem Gate gescheitert, ein Startproblem und kein Gate-Befund. Er verweist auf `SYSTEM-REQUIREMENTS.md`. Das Gate bleibt rot. Ein Python-Traceback beginnt mit `Traceback` und trifft das nicht.
- [x] P4: `docs/SYSTEM-REQUIREMENTS.md` („Gerenderte Zielrepos“):
  - Der erste Gate-Lauf über uv braucht den Paket-Index oder einen gefüllten uv-Cache.
  - Ohne Paket-Index braucht es Python ≥ 3.11 mit PyYAML ≥ 6. Die Hooks kommen dann über `python3 scripts/process/install_hooks.py`; dieser Weg startet Runner und Gates mit diesem Python.
  - Das pre-commit-Framework selbst kommt von PyPI (`uvx pre-commit`), und seine Einträge starten über `uv run`. Für eine Sandbox ohne PyPI ist es nicht geeignet.
  - Der Satz „eine systemweite PyYAML-Installation ist nicht erforderlich“ und Zeile 70 („die Gate-Logik läuft danach über uv“) werden entsprechend eingeschränkt.

**Tests.** Rot vor dem Fix:

1. Ein ausgeliefertes Gate (`gate_runner.py`, `pyyaml>=6,<7`) mit `cmd[0] == sys.executable` und PyYAML 6: Das Kommando bleibt unverändert, obwohl `uv` auf PATH liegt.
2. `declared_dependencies` liest `["pyyaml>=6,<7"]` als eine Anforderung, ebenso ein mehrzeiliges Array.
3. Ein Kind, das über uv startet und scheitert (lokales Gate mit einer nicht installierten Abhängigkeit, `uv`-Stub mit uv-Fehlerform): Der Gate-Abschnitt nennt das Startproblem, das Gate bleibt rot. Das gilt für rc 1 und für rc 2.
4. Der Pre-push-Rahmen startet den Runner über einen `uv`-Stub, der scheitert: Die Meldung nennt das Startproblem.

Schutz (schon vorher grün, bleiben grün):

5. Vergleiche, parametrisiert: `>=99`, eine fehlende Distribution, Extras, Marker, `~=`, `===`, eine `rc`-Version, `6.0` gegen `>6`, ein anderes `cmd[0]` (auch ein Symlink auf `sys.executable`), ein nicht erfülltes `requires-python`, eine Distribution ohne auffindbares Modul. Jeder dieser Fälle läuft über uv.
6. Ein Gate, das mit rc 2 und Ausgabe endet, oder ein Traceback ohne uv-Form: Es gibt keine Startproblem-Meldung.

Nachweis: Das Sandbox-Experiment läuft erneut, mit GitHub-Modell, PyPI gesperrt, Hooks über `install_hooks.py`. Der Runner läuft mit `python3` durch, und der Push an ein lokales Remote geht durch den Pre-push-Rahmen.
