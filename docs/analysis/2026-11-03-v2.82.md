# v2.82 — Spec-Kit-Skills erreichen jeden Klon

issue: #363
tier: 3

## Anlass

Das Modul `speckit` richtet Spec Kit über `specify init` ein. Der Befehl schreibt die `/speckit-*`-Skills in das Skill-Verzeichnis des Harness, bei Claude Code nach `.claude/skills/`. Laut Moduldoku braucht zur Laufzeit nichts das CLI. Das stimmt nur, wenn die Skills committet sind.

In Kenni ist das nicht der Fall:

- `.gitignore:26` schließt `.claude/skills/` aus, seit `3bcd9b9bcc` (2026-04-15, „per-user Claude Code state“). Das war vier Monate vor Spec Kit.
- `specify init` lief am 2026-08-08. Die Skills landeten im ignorierten Verzeichnis. `git status` zeigte nichts, es gab weder Fehler noch Hinweis.
- `.specify/integrations/claude.manifest.json` listet zehn Skill-Dateien, keine davon ist getrackt.
- Skripte und Vorlagen unter `.specify/` sind dagegen committet.

Jeder frische Klon hat deshalb kein `/speckit-specify`, `-clarify`, `-plan` und `-tasks`. Das gilt für Cloud-Sessions, Worktrees und einen zweiten Host. Zurück kommen die Skills nur, wenn man `specify-cli` installiert. Das kann eine Sandbox verweigern; der Owner ist in einem Projekt genau daran gescheitert.

Ein Test in einem Scratch-Repo zeigt außerdem: Die Ausnahme aus #363 (`!.claude/skills/speckit-*/` neben `.claude/skills/`) wirkt nicht. Git schließt nichts wieder ein, dessen Elternverzeichnis ausgeschlossen ist. Erst `.claude/skills/*` mit der Ausnahme danach macht die Skills sichtbar (Kommentar auf #363).

## Umfang

| Paket | Inhalt |
|---|---|
| D | `speckit.md`, Abschnitt „Setup“: Skills committen, die richtige `.gitignore`-Form, die genutzten Skills benennen. Dasselbe für Upgrades. |
| G | Gate `speckit`: weicher Hinweis, wenn eine Skill-Datei aus einem Integrations-Manifest fehlt oder nicht getrackt ist. Dazu ein Hinweis, wenn es kein Manifest gibt. |

Nicht in diesem Release:

- Das Template liefert die Spec-Kit-Laufzeit selbst aus, damit kein Projekt `specify-cli` braucht (#364). Das ist Tier 3, ein eigenes Vorhaben und eine Vertragsänderung des Moduls.
- Das `eval` in `setup-plan.sh` ist Upstream-Code.
- Die `.gitignore` eines Projekts. Das Template ändert keine bestehenden Projektdateien (Brownfield). Den Schritt nennen die Update-Hinweise.

## Begriffe

- **Integrations-Manifest:** `.specify/integrations/<integration>.manifest.json`. Spec Kit 0.16 schreibt es je Integration. Unter `files` stehen die installierten Pfade mit Hash. `speckit.manifest.json` ist der Kern (Skripte und Vorlagen), kein Harness.
- **Spec-Kit-Skill-Datei:** ein Pfad aus einem Harness-Manifest, dessen Pfadteil mit `speckit-<name>` oder `speckit.<name>` beginnt, also `.claude/skills/speckit-plan/SKILL.md` oder `.agents/commands/speckit.plan.md`. Der Name ist das erste Wort nach `speckit` und dem Trenner.
- **Bewusst entfernt:** `constitution`, `implement` und `taskstoissues`. Das Setup löscht sie (`speckit.md`, „Setup“). Sie stehen weiter im Manifest, und das Gate prüft sie nicht.

## Aufgaben

- [ ] D1: Abschnitt „Setup“ in `speckit.md`, nach den `rm`-Zeilen:
  - Die übrigen Skills werden committet, zusammen mit `.specify/`. Der Grund steht im Text: Ein frischer Klon hat sonst keine `/speckit-*`-Befehle, und das CLI soll zur Laufzeit nicht nötig sein.
  - Ignoriert ein Projekt sein Skill-Verzeichnis als Ganzes, ändert es die Regel auf `<dir>/*` und setzt `!<dir>/speckit-*/` dahinter. Der Text sagt, warum `!` allein nicht wirkt.
  - Der Code-Block bekommt `git add .specify <skills-dir>/speckit-*` vor den Gate-Lauf.
- [ ] D2: Der Absatz unter dem Code-Block nennt die Skills, die der Ablauf nutzt: specify, clarify, plan und tasks; analyze und converge für Tier 3; checklist auf Wunsch. Er nennt sie getrennt von den drei entfernten.
- [ ] D3: „Upgrades“: nach `specify init --here --force` die drei Skills wieder entfernen und die neuen Skill-Dateien im selben `chore:`-Commit committen.
- [ ] D4: „What the gate enforces“ bekommt eine SOFT-Zeile für den neuen Hinweis.
- [ ] G1: `check_speckit.py`, neue Funktion `_skill_notes(root) -> list[str]`, aufgerufen in `check()` nach der Prüfung des Constitution-Zeigers.
  - Sie liest jede `.specify/integrations/*.manifest.json` außer `speckit.manifest.json` und sammelt die Spec-Kit-Skill-Dateien ohne die drei entfernten.
  - Gibt es kein Harness-Manifest, kommt ein Hinweis: `specify init` ist hier nicht gelaufen, kein `/speckit-*`-Skill ist installiert, siehe „Setup“.
  - Ist ein Manifest nicht lesbar (JSON-Fehler, kein `files`-Objekt), kommt ein Hinweis, der die Datei nennt. Ein gescheiterter Lesevorgang ist nie „alles da“ (#285).
  - Fehlt eine Datei auf der Platte, kommt ein Hinweis mit Anzahl und bis zu drei Pfaden: „this checkout has no /speckit-<name>“, wiederherstellen aus Git oder per Setup.
  - Liegt eine Datei auf der Platte, ist aber nicht getrackt (`git ls-files -z -- <pfade>`), kommt ein Hinweis mit Anzahl und bis zu drei Pfaden: „a fresh clone or worktree lacks them; commit them (Setup)“. Ist der Pfad ignoriert, nennt `git check-ignore -v` die Regel, etwa `.gitignore:26 .claude/skills/`.
  - Scheitert `git ls-files`, etwa weil das kein Git-Arbeitsbaum ist, kommt ein Hinweis: ob die Skills committet sind, ist ungeprüft.
  - Alles bleibt weich. Das Gate blockiert nie wegen eines Skills (#363 AC-3).
- [ ] G2: Docstring von `check_speckit.py` um die SOFT-Zeile ergänzen.

## Tests (je rot vor dem Fix)

In `tests/test_speckit.py`, mit einem Helfer, der ein gerendertes Projekt zu einem Git-Repo macht und ein Manifest samt Skill-Dateien anlegt:

1. Die Skills sind committet: keine Skill-Notiz, Gate grün.
2. `.gitignore` enthält `.claude/skills/`, die Skills liegen auf der Platte: Die Notiz nennt die Anzahl, einen Pfad und die Regel `.gitignore:1`. Das Gate bleibt grün (rc 0).
3. Eine Skill-Datei aus dem Manifest fehlt: Die Notiz nennt `/speckit-plan` als fehlend.
4. Die entfernten Skills fehlen und stehen im Manifest: keine Notiz.
5. Kein Harness-Manifest, nur `speckit.manifest.json`, oder gar keins: Notiz, dass `specify init` nicht gelaufen ist. Auf einem frischen Render bleibt das Gate grün (der bestehende Test `test_gate_soft_before_init_is_impossible_here` bleibt gültig).
6. Ein unlesbares Manifest: Notiz nennt die Datei, das Gate bleibt grün.
7. Kein Git-Repo, das Manifest vorhanden: Notiz „ungeprüft“, das Gate bleibt grün.
8. Die Form aus der Doku wirkt wirklich: `.claude/skills/*` mit `!.claude/skills/speckit-*/` macht die Skill-Datei für `git status` sichtbar, `.claude/skills/` mit derselben Ausnahme nicht. Der Test liest beide Formen aus `speckit.md`, damit Doku und Verhalten nicht auseinanderlaufen.
9. Ein Manifest, das Befehle statt Skills schreibt (`.agents/commands/speckit.plan.md`): wird genauso geprüft.
