## The owner's intent (verbatim where it matters, translated)

- **Gates apply by content, not by a project switch.** "Gates should be activated as needed — fitting the content requirements. If no UI is contained, I need no UI gates. If no backend is contained, I need no backend gates." A first draft read this as per-project opt-in; the owner corrected that explicitly.
- **Non-product changes must not run the software chain.** Uploading images, or loading a small setting in another repo, went through the whole chain meant for software development. It does not happen often, but each time it is a nuisance. The friction was high enough that host-local agent tooling was moved out into a separate repository (kenni-tooling), outside the process.
- **UI work: considered, not judged.** "I know a gate cannot check UI quality. But for UI changes certain standards must at least have been considered: that there is a design board, that navigation forward and back was thought through, different sizes, and so on — in the end what is in this matrix." The product fills the matrix; the template guarantees that it exists with certain structural features.
- **No looking back.** "Existing design concepts and contracts are fine; we leave them as they are. For future changes it must be followed."
- **No bureaucracy.** "I don't want to build a huge bureaucratic act. The whole thing must stay manageable."
- **Two levels.** A design concept for one issue (one surface revised) differs from a design contract that governs many issues. The owner was not sure how to handle that.
