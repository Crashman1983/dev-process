## Paket N — Entwurf (#262, #263-Folgefrage)

**Befund (Code, v2.74.2):**
- `template_verify._verify` setzt `acknowledged` nur bei `ack.base == base` (Fork-Point von Tip und Integrations-Ref) und `ack.release == new_sha`.
- `check_review.template_review_findings` zählt nur volle Pässe mit `r.base == update.base`.
- Die gewöhnliche Abdeckung (`_history`, Step B) verträgt einen weitergelaufenen main schon: Ein Review zählt ganz, wenn seine Basis auf main liegt und git den Merge selbst sauber auflöst (#158). Strikt ist allein die Basis-Gleichheit der beiden Update-Prüfungen. Ein Zug, der auf einen weitergelaufenen main merged, verliert damit Ack und Update-REVIEW, auch wenn main das Update nicht berührt hat (Kenni #2631, #2621-Zug).

**Entscheidungen:**
- N1 — **Ein Owner** `template_verify.carried_base(root, old_base, base, update) -> bool`. Wahr, wenn alle drei Bedingungen gelten:
  - `old_base == base`, oder `old_base` ist Vorfahr von `base`;
  - `git diff --name-only old_base base` trifft keinen dieser Pfade: `.copier-answers.yml`, die Ack-Datei, `.process-owned`, die Update-Pfade (`identical` ∪ `project_delta`) und die Pfade, die einer der beiden Renders ablegt;
  - git kann beides beantworten (fail closed).
- N2 — **Ack:** `acknowledged` gilt bei `ack.release == new_sha`, `owner` gesetzt und `carried_base(ack.base, base)`. Ein Release-Wechsel verlangt weiter ein neues Ack.
- N3 — **Update-REVIEW:** `template_review_findings` nimmt volle Pässe mit `carried_base(r.base, update.base)` statt Gleichheit. Die Inhaltsabdeckung bleibt unverändert: `_unreviewed_paths(root, r.head, tip, …, r.base) == set()`.
- N4 — **Was weiter verfällt:**
  - ein main-Commit, der eine der Pfade aus N1 ändert;
  - ein Release-Wechsel;
  - eine Basis, die kein Vorfahr ist (Rebase auf einen anderen Stand);
  - ein git-Fehler.
  Die Meldung nennt den Grund („main changed `<path>` since the acknowledged base“).
- N5 — **#263-Folgefrage (Zug):** Läuft der Retry mit dem Projekt-Befehl `--retry` (Weg `failed`), ist ein Grün kein Beleg für Flakiness auf identischem Befehl.
  - Das Log und die Meldung sagen dann „green under the retry command `<retry>`, red under the suite `<suite>` — flaky, or the two commands differ (flags, environment)“. Der Merge läuft wie heute weiter.
  - Wiederholt sich derselbe Unterschied, fängt ihn der pre-push mit der vollen `merge_suite` ab (so geschehen).
  - Kein zweiter Voll-Lauf: Er würde jeden echten Flake doppelt kosten.
- N6 — **Robustheit:** `check_review.py` deklariert `PyYAML` im PEP-723-Kopf (#262 AC-4). `gate_invoke.child_argv` startet es dann über `uv run --script`, so wie heute schon jedes Skript mit eigener Deklaration.

**AC (EARS):**
- AC-N1: When main moved only through commits that touch none of the N1 paths, an ack for the same release shall stay acknowledged and a full update REVIEW on the older base shall still cover the update.
- AC-N2: When a main commit since the acknowledged base touches an N1 path, the ack and that REVIEW shall expire, and the finding shall name the path.
- AC-N3: When the release SHA differs, or the old base is no ancestor of the new one, or git cannot tell, nothing shall be carried.
- AC-N4: When the train's retry ran the `--retry` command and passed, its log and message shall name both commands and shall not claim an identical run.
- AC-N5: `check_review.py` shall run standalone on a main push without a pre-installed PyYAML.

**Unabhängige Durchsetzung:** N lockert eine Bindung, deshalb Refute vor Review-Runde 1. Die Inhaltsprüfung (`_unreviewed_paths`) bleibt die Hürde für Code. N ändert nur, welche Basis als „dieselbe Update-Lage“ gilt.
