## Aufgaben v2.97

- [ ] B1 `[design]` **Block `steering` im Mandat, eine Besitzerin.**
  - Neues Kernmodul-Stück `optimize.steering(root) -> (settings, problems)` nach dem Muster von `plan_drift.settings`: Schlüssel und Namen wie in Kennis Block, damit Kennis Datei unverändert gilt — `tracks` (Name → Beschreibung), `wip_per_track`, `process_issues_in_progress`, `process_share_max` (0–1), `process_share_window_weeks`, `kit_update_cadence_days`; neu `growth_max_commits`, `growth_max_days` (#413).
  - Fehlt ein Schlüssel, gibt es keine Grenze. Ein falscher Typ wird als Problem genannt und ignoriert, nie geraten.
  - `optimization.example.json` zeigt den Block; der `_comment` nennt die Leser.
- [ ] B2 `[design]` **In Arbeit hat eine Besitzerin im Kern (r1 M4, M5, m6, n15).**
  - `tower.in_progress(root, *, fetch=True)` liest `dispatch.records()` und `report.read_reports` direkt, nicht `tower.sessions` (schwer, zirkulär).
  - **Beide Hosts:** vorher `report.fetch_reports` mit kurzer Frist; misslingt er, sagt das Ergebnis „other hosts not read — may undercount“. Ist `steering` gesetzt, setzt dispatch für seine Worker `PROCESS_REPORT_SYNC=1` (über `worker_vars`, dispatch.py:2329), damit jeder Bericht veröffentlicht wird. Übergabe-Records an einen anderen Host (`state=remote`) zählen als in Arbeit.
  - **In Arbeit:** das Issue des letzten Berichts je Worker, Zustand nicht `done`, `idle` oder `failed` (wie `tower.PARKED`), oder ein dispatch-Record ohne Bericht. **Veraltet:** kein Bericht und kein Record seit `STALE_DAYS = 14` ⇒ als „stale“ gezeigt, nicht gezählt.
  - **Track je Issue:** aus dem Record oder dem Bericht (neues optionales Feld `track` in `write_report`, gesetzt über `PROCESS_TRACK` aus `worker_vars`); sonst „untracked“. Untracked wird gezeigt und zählt gegen keinen Track; `dispatch.py track --issue N --track <name>` trägt den Track für Arbeit nach, die vor dem Update begann.
  - **Claim-Zeit:** der erste Record oder Bericht der aktuellen Strecke zum Issue, nur aus Records und Berichten, ohne `gh`.
  - Der Tower-Teil von `intake` (v2.96 A2) ruft diese Funktion statt einer eigenen Regel.
- [ ] B3 `[design]` **WIP-Grenze beim ersten Start einer Arbeit (#412 AC-3; r1 M2, M3, m7).**
  - Geprüft wird in `dispatch.py start` bei **jeder Phase, wenn das Issue noch nicht in Arbeit ist** (B2) — also Brainstorm, Plan oder ein Quick-Execute ohne Plan (dispatch.py:2287-2291), nicht am Phasennamen.
  - `--track <name>` ist dann Pflicht, sobald `steering.tracks` gesetzt ist; `process` ist der feste Name für Prozessarbeit (Grenze `process_issues_in_progress`), jeder andere Name muss in `tracks` stehen.
  - Ist der Track an seiner Grenze, verweigert `start` mit Exit 3 und nennt Grenze, Track und die Issues darin. `--over-wip "<Grund>"` startet trotzdem und schreibt ein `gate_events`-Ereignis mit `override=` wie `--stale-plan-ok` (plan_drift.py:227-233); die Journalzeile bleibt Sache des Stewards, der dafür eine `DECISION` des Owners braucht.
  - **Warteschlange:** `queue add` nimmt `--track` und `--over-wip` und speichert sie (dispatch.py:2990-3006); `drain` reicht sie an `start` weiter (:3018-3021). Eine Verweigerung wegen WIP lässt die Zeile warten.
  - `STEWARD` Schritt 4: wähle das nächste Ready-Issue eines Tracks unter seiner Grenze; Tracks aus dem Mandat, Zuordnung über das Label `track:<name>` oder die Angabe des Owners.
- [ ] B4 `[design]` **Hinweis bei wachsenden Issues (#413 `warn`; r1 m11, m12).**
  - Beim Start einer Plan- oder Execute-Phase (nicht Review) zählt dispatch für das Issue die Commits auf seinen Branches (`--no-merges`, `<branch> --not <integration>`) und die Tage seit der Claim-Zeit aus B2. Über `growth_max_commits` oder `growth_max_days`: eine Zeile an den Steward (stderr) und eine Notiz „split or finish“ im Worker-Prompt, wie `plan_drift` im Modus `warn`. Verweigert nie, kein `gh`.
  - Die Zählung der Branch-Commits ist eine Kernfunktion `tower.issue_branch_commits(root, issue, since)`; `intake` (v2.96 A2, `branch_commits`) nutzt dieselbe. Der v2.96-Plan wird entsprechend angepasst.
- [ ] B5 `[mechanical]` **Prozessanteil im Wochenlauf (#416; r1 m8).**
