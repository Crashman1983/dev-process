- [ ] G1 **Grabstein (#428; r1 M2, M3, M4, N2, N3).**
  - Marker ist das Story-Feld `retired_into`: eine Liste von Story-IDs, in denen der Inhalt aufging, leer für „ohne Nachfolger“. Ist der Schlüssel vorhanden, ist die Story ein Grabstein. `rc.is_tombstone(data)` ist der eine Eigentümer, für Gate, Filter und künftige Ansichten.
  - Hart für einen Grabstein:
    - `acceptance` fehlt oder ist nicht `[]`: ein aktives Item (AC-3), und ein fehlender Schlüssel würde den stable-id-Vergleich überspringen (cfr:593-594);
    - `retired` ist leer;
    - `retired_into` ist keine Liste von Strings;
    - ein Eintrag nennt keine bekannte Story oder die Story selbst, oder die Kette über Grabsteine endet in einem Zyklus. Ketten sind erlaubt, damit eine spätere Stilllegung keine anderen Grabsteine umschreiben muss (r2 N2);
    - ein `retired`-Eintrag trägt `split_into`;
    - `tests` bzw. `test_mapping` ist nicht leer.
  - Befreit: Testpflicht, `status`-Pflicht (ein vorhandenes `status` muss weiter gültig sein) und Issue-Pflicht. `_under_granular_note` braucht keine Ausnahme, denn ein Grabstein hat keine Tests.
  - Eine leere `acceptance` ohne `retired_into` bleibt hart; die Meldung nennt `retired_into`.
  - `stable_ids` (AC-4): Eine eigene Schleife über die Stories der Basis, gepaart nach **ID**, nicht nach Pfad. Ein Grabstein der Basis, dessen ID auf dem Branch fehlt, ist hart („a retired story stays as its tombstone“). Entfernt ein Branch `retired_into` wieder, ist das eine Wiederbelebung nach den bestehenden Regeln: neue Item-IDs liegen über allen alten. Eine neue Story mit der ID eines Grabsteins ist schon heute eine doppelte ID.
  - Verweis `SID#ACn` auf ein Item eines Grabsteins: ein Hinweis, der `retired_into` nennt. Bei leerem `retired_into` bleibt er hart, wie ein retired Item ohne `split_into` (cfr:672-674).
  - Plan-Gate und Produkt-Rahmen ändern sich nicht. Tests pinnen AC-2: ein Plan, der eine Grabstein-ID nennt, ist grün; derselbe Plan mit gelöschter Story ist rot. Die Fixture legt dafür `feature-registry.local.json` an der Integrations-Ref an (check_plan_structure.py:507-508), sonst ist die rote Hälfte leer.
  - Doku: Abschnitt „Retiring a story“ in `feature-registry.md.jinja`, mit Beispiel, Wann-löschen-wann-Grabstein und dem Hinweis, dass zwei für sich grüne Branches gemeinsam rot werden können, wenn sie einen Zyklus schließen; der Zug fängt es im gemeinsamen Lauf (train.py:1462), der zweite Passagier fällt heraus. `_comment` in `feature-registry.json`. `retired_into` kommt in `_known_fields`.
- [ ] G2 **Basis hinter einem integrierten Tip (#429; r1 B2, M6; r2 M1–M3, M5, N3, N6, N8).**
  - (a) Enthält ein Remote-Ref den Tip, wird ein lokaler Ref desselben Branch-Namens übersprungen, wenn er ein Vorfahr dieses Remote-Refs ist, also nur hinterherhinkt. Dasselbe gilt für ein nicht-primäres Remote, das hinter einem enthaltenden Remote liegt. Liefert kein anderer Ref eine Basis, gilt das heutige Ergebnis für einen Tip auf dem Integrations-Ref (AC-2). Ein lokaler Ref, der *vor* dem Remote liegt oder abweicht, entscheidet weiter (`forged-master`, `ff-main`, test_review.py:1439).
  - Die Regel „hinkt nur hinterher“ ist eine Funktion, und `_integration_base` und `_integration_ref` (cr:2116-2142, der zweite Eigentümer; er gibt heute dem `_history` und dem `merged_work` das alte lokale main) nutzen beide sie.
  - (b) **Auf einem Merge-Push kommt die Basis vom Server.** `pre_push` reicht die `remote_sha` der Ref-Zeile auf das Integrationsziel als `PROCESS_PUSH_BASE` an die Gates weiter, so wie heute schon `PROCESS_PUSH_TARGETS` (pre_push.py:146-149). Ein Wert von außen wird überschrieben.
    - Ist sie gesetzt, nimmt `_integration_base` `fork_point(remote_sha, tip)` und schaut auf keinen lokalen oder Tracking-Ref. Die Server-SHA ist das, was main gerade ist; ein gefälschtes `origin/main` spielt keine Rolle mehr.
    - `remote_sha` aus lauter Nullen (der Push legt main an): keine Basis, wie heute bei einem Repo ohne Integrations-Ref auf einem Push nach main (hart, `NO_INTEGRATION_REF`).
    - Eine `remote_sha`, die dieser Klon nicht kennt: hart, „fetch first“.
    - Ohne Remote-Namen, ohne Abbildung über `remote.<name>.fetch`, ohne neue Fixture-Pflicht für bestehende Tests (r2 M1, M2, N8).
    - Ein Race zwischen Abruf und Push erreicht den Hook nicht: git verwirft Updates, die nicht fast-forward sind, selbst (r2 M2).
  - Der Zug bekommt keinen Abbruch beim gescheiterten Abruf.
  - Tests:
